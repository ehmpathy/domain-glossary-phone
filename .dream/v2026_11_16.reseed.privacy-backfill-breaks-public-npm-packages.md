# 🌙 dream: implicit-package-privacy must not silently mark a public npm package private

- kind: reseed
- owner: ehmpathy/declapract-typescript-ehmpathy
- caught 2026-11-16

## .the cue that fired

a declapract upgrade on a public, published npm package (`domain-glossary-phone`, npm 1.4.1, github PUBLIC) backfilled `"private": true`. no gate caught it; it would have broken the next tag publish and flipped the github repo private on the next `provision` apply.

## .the gap, precisely

`src/practices/provision-github/bad-practices/implicit-package-privacy/package.json.declapract.ts`, lines 22–35: absent or non-boolean `private` → `private: true`, blind to use case. `useCases.yml` `npm-package` ships both `cicd-package` (`npm publish --access public`) and `provision-github`, so the backfill contradicts its peer practice for every public package that predates the key.

## .the shape of the fix

- in `npm-package`, refuse to backfill and fail loud with the choice (`"private": false` for a public package, `true` otherwise), or derive the value from reality (published on npm / github repo public)
- clamp: npm-package fixture with no `private` key → apply never yields `private: true` silently

## .why it is not done in this round

the practice lives in another repo; this route repairs the consumer (`"private": false`) and records the upstream defect.
