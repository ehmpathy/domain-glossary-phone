## D1 — practice bug: the ts-node removal can never fire beside the tests-node practice

- the practice that should have removed `ts-node` exists: `src/practices/typescript-any/bad-practices/ts-node-beside-esbuild-register/package.json.declapract.ts`
- it fired in neither apply pass of the exec, though pass 2 ran with both preconditions met (`esbuild-register` declared; all four `jest.*.config.ts` carry `@jest-config-loader`)
- root cause, lines 43–51 (unchanged on upstream `origin/main`):
  ```ts
  // a root jest .ts config that jest would load via ts-node
  return readdirSync(root)
    .filter((name) => /^jest\..*\.ts$/.test(name))
    .some((name) => !readFileSync(path.join(root, name), 'utf-8').includes('@jest-config-loader'));
  ```
  the filter `^jest\..*\.ts$` matches every root `jest.*.ts`, not just configs. the tests-node practice itself ships six non-config files that match and never carry the pragma:
  `jest.unit.env.ts`, `jest.integration.env.ts`, `jest.integration.env.db.ts`, `jest.acceptance.env.ts`, `jest.integration.prepare.ts`, `jest.acceptance.prepare.ts`
  → `isTsNodeStillUsed` returns `true` in every repo on tests-node → the fix is dead code there
- other gates ruled out:
  - scripts: no package.json command names `ts-node`
  - import scan (`isPackageImportedInRepo`, `dirs: ['.']`): a grep with its exact regex over `.agent/` and the repo finds no import; its walker (`getAllPathsUnderDir`) uses `Dirent.isDirectory()`, false for a symlink, so the 82 role symlinks under `.agent/` are never descended
- suggested fix upstream: narrow the filter to configs, `/^jest\.(.+\.)?config\.ts$/`, so env and prepare files do not count. add a clamp: a fixture repo with the tests-node env/prepare files + pragma'd configs → `ts-node` removed
  - how each non-config file loads (from the configs): `jest.*.env.ts` via `setupFilesAfterEnv`; `jest.*.prepare.ts` via `globalSetup`. jest documents that it applies the project `transform` (`@swc/jest`) to both, so neither reaches for `ts-node`
  - unverified here: this repo has zero integration/acceptance tests, so jest never ran a `prepare` globalSetup after `ts-node` left. the upstream clamp must run a real `globalSetup: './jest.*.prepare.ts'` without `ts-node` installed before the filter narrows
- consequence for every repo on this upgrade: `test:lint` fails on depcheck until `ts-node` is removed by hand
- why upstream's own clamp stays green: `gh search code --repo ehmpathy/declapract-typescript-ehmpathy "jest-config-loader"` surfaces the clamp fixture `src/.test/assets/tool-swap-removals/repo-after-swaps/`, which holds only `declapract.use.yml`, `jest.unit.config.ts`, `package.json`, `tsconfig.json` — no env or prepare file, so the filter never meets the case that breaks it
- link: https://github.com/ehmpathy/declapract-typescript-ehmpathy/blob/9b0da949d344da643227bcda93230c5572472f78/src/practices/typescript-any/bad-practices/ts-node-beside-esbuild-register/package.json.declapract.ts
- prior issue: #660 (CLOSED) introduced this practice; its fix is the one that cannot fire. no open issue covers it

## D2 — practice bug: privacy backfill contradicts public publish in the npm-package use case

- the practice: `src/practices/provision-github/bad-practices/implicit-package-privacy/package.json.declapract.ts`
- lines 22–35: when `private` is absent or non-boolean, `asPackageJsonWithPrivacyExplicit` sets `private: true`, with no regard for use case
- `useCases.yml` → `npm-package` (line 42) includes both `cicd-package` (line 47) and `provision-github` (line 49)
  - `cicd-package` ships `.publish-npm.yml` → `npm publish --access public --provenance`
  - npm refuses to publish a package marked `"private": true`
  - `provision/github.repo/resources.ts:48` maps `private !== false` → github `visibility: 'private'`
- so for every public npm package that lacks the key — the norm for packages made before this practice — the backfill silently (a) breaks the next tag publish and (b) makes the next `provision` apply flip the github repo private
- fail-closed is right for a service repo; it is wrong as a silent default where the same use case publishes publicly
- suggested fix upstream, either:
  - in `npm-package`, derive the backfill from reality (e.g. `npm view <name>` exists, or the github repo is public) and write that, or
  - refuse to backfill and fail loud with the choice for a human: `"private": false` (public package) vs `true`
- add a clamp: an npm-package fixture with no `private` key must not come out `private: true` silently
- link: https://github.com/ehmpathy/declapract-typescript-ehmpathy/blob/9b0da949d344da643227bcda93230c5572472f78/src/practices/provision-github/bad-practices/implicit-package-privacy/package.json.declapract.ts (found via `gh search code --repo ehmpathy/declapract-typescript-ehmpathy "asPackageJsonWithPrivacyExplicit"`)
- prior issue: none — `gh issue list --state all --search "private in:title"` → empty

## why neither is a repo quirk

- D1 reproduces in any repo with the tests-node practice; this repo has no custom jest files — the exec log shows tests-node wrote nine of the ten root `jest.*.ts` (`fix:applied`), and the tenth, `jest.unit.env.ts`, is absent from the diff because it already matched the practice template (`tests-node/best-practice/jest.unit.env.ts.declapract.ts`)
- D2 reproduces in any `npm-package` repo created before `implicit-package-privacy`; this repo's only trait is that it is a normal public package
